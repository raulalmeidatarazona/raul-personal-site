But we now have another problem.

The streamer is producing events that still look too much like the database that created them.

And that is dangerous.

Because a database schema is an implementation detail.

A public event contract should not be.

This article is about the next architectural boundary:

Turning database changes into stable, transport-independent events and introducing a durable message broker between producers and consumers.

The goal is to reach a point where the ERP can continue evolving internally while downstream systems consume a stable event contract.

Why CloudEvents?

This is where CloudEvents becomes useful.

CloudEvents is a specification designed to provide a common way of describing event data through standardized metadata, making event producers, routers and consumers less dependent on the specific format used by each event source. CloudEvents is now a CNCF Graduated project and provides SDKs for multiple languages, including Go.

The important idea is not “another JSON format”.

It is standardized event metadata.

A CloudEvent identifies things such as:

  • what happened,

  • where it came from,

  • which event instance this is,

  • which CloudEvents specification version is being used,

  • and optionally when it happened and other extension attributes.

At the core, the event starts to look like this:

{
  "specversion": "1.0",
  "type": "com.example.erp.stock.updated",
  "source": "/erp/inventory",
  "id": "8b7b9a80-2f2e-4a77-8f5e-0a81b8a0d4d1",
  "time": "2026-09-10T12:30:45Z",
  "datacontenttype": "application/json",
  "data": {
    "article_id": "12345",
    "previous_stock": 10,
    "current_stock": 9,
    "warehouse_id": "MAD-01"
  }
}

Now the consumer sees an event contract rather than a MySQL row mutation.

The Broker as a Temporal Boundary

The message broker changes the equation.

Now the architecture becomes:

The broker introduces temporal decoupling.

The producer and consumer no longer have to be available at exactly the same time.

The producer can publish.

The broker retains the message according to its configured durability and retention semantics.

The consumer processes it when it is able to do so.

That is a fundamentally different relationship.

RabbitMQ or NATS JetStream?

At this point, we have several reasonable choices.

For a lightweight architecture, two interesting candidates are:

RabbitMQ

and

NATS JetStream

They are not identical products and they should not be treated as interchangeable in every workload.

The architectural requirement is what matters:

We need a broker that can provide durable asynchronous delivery and explicit acknowledgement semantics appropriate to the workload.

RabbitMQ supports publisher confirms on the producer side and consumer acknowledgements on the consumer side. RabbitMQ documents these mechanisms as the foundation for at-least-once delivery, while also warning that retransmission after failures can produce duplicates.

That has an immediate architectural consequence:

At-least-once delivery means consumers must be prepared for duplicates.

We will return to that in the next article.

Building a CloudEvent in Go

The CloudEvents project maintains an official Go SDK for creating, serializing and transmitting CloudEvents. The current SDK supports CloudEvents 1.0 and its current v2 module requires Go 1.24+.

Instead of maintaining our own CloudEvent structure, the production implementation can use the official SDK.

A simplified example:

package main

import (
	"time"

	cloudevents "github.com/cloudevents/sdk-go/v2"
)

type StockUpdated struct {
	ArticleID     string `json:"article_id"`
	WarehouseID   string `json:"warehouse_id"`
	PreviousStock int    `json:"previous_stock"`
	CurrentStock  int    `json:"current_stock"`
}

func BuildStockUpdated(
	id string,
	data StockUpdated,
) cloudevents.Event {

	event := cloudevents.NewEvent()

	event.SetID(id)
	event.SetSource("/erp/inventory")
	event.SetType("com.example.erp.stock.updated")
	event.SetTime(time.Now().UTC())

	_ = event.SetData(
		cloudevents.ApplicationJSON,
		data,
	)

	return event
}

This is better than manually recreating the CloudEvents envelope because the official SDK already provides the model and serialization support.

What We Actually Gained

The result is not simply “we added RabbitMQ.”

We gained four important properties.

1. Schema Decoupling

Consumers no longer depend directly on MySQL table structures.

2. Temporal Decoupling

The producer and consumer no longer need to be available at the same time.

3. Transport Independence

The event contract can move through different transports without changing the domain meaning of the event.

4. Controlled Backpressure

The broker provides a durable buffering boundary instead of forcing the CDC process to retain an unlimited backlog in memory.

These properties are more important than the specific broker technology.

The Golden Rule

The lesson from the first three articles can now be summarized as:

Keep database transactions local, convert database changes into stable domain events, and introduce a durable asynchronous boundary before the network of consumers.

The full evolution looks like this:

The database remains responsible for transactional truth.

The CDC layer is responsible for transporting change.

The event contract is responsible for semantic stability.

The broker is responsible for temporal decoupling.

The consumer is responsible for business processing.

That separation is what makes the architecture manageable.
